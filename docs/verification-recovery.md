# Verification recovery

A failed verification does not necessarily mean the implementation failed. Preserve the task files and inspect the bounded verification result before spending another implementation round.

Before starting the project verification command, Relay prepares ignored Vite cache directories through the physical dependency directory. It refuses a cache redirected through a link. For an installed Electron dependency, it checks the executable and distribution version without importing its entry point or triggering its automatic installer, and passes the physical distribution to the command. Missing tooling stops before the long script starts.

Known Electron installation failures are infrastructure failures. A stored unknown result containing that evidence can be routed to verification recovery without rewriting the historical result. Evidence of an assertion failure alongside infrastructure failure remains unknown and uses bounded diagnosis.

Ornith read_file validates UTF-8 and returns raw-byte sha256, totalBytes, whole-file lineEnding, utf8Bom and trailingLfBytes. These values describe the complete file, even when only a slice of content is returned. A UTF-8 BOM is omitted from decoded content but is reported explicitly. Exact-text checks require the complete content and the requested byte-format metadata, not just a slice or Git status.

The project test suite does not automatically check the contents of a newly created document. Specifications must use file-read evidence for such requirements unless an existing test was inspected or adding a test is within scope. A correct file created in an earlier task round must be preserved during recovery.

An explicit specification regeneration is available in the expanded Specification panel for a grounded task after a failed round. It preserves files and invalidates approval; the new specification requires its own review and approval. It does not mark the old failed runs successful.

After an implementation round, regeneration can describe preserved uncommitted task files. Its grounding record includes a SHA-256 identity of all tracked and non-ignored new file bytes, modes, paths, HEAD and branch. Two captures must agree before Codex reads; capture and branch binding are checked again before storing the plan and before plan review. A changed fingerprint starts a fresh Codex thread. Old dirty records without this identity remain untrusted, and first-round dirty generation is still refused. No commit, staging, reset or discard is performed.
